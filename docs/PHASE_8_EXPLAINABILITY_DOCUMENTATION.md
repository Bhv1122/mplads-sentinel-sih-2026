# Phase 8: Explainability Layer Specification & Documentation

## 1. Overview & Architectural Philosophy

The **Explainability Layer** bridges the gap between complex numerical anomaly detection and actionable governance in the MPLADS project risk detection system.

```
+---------------------------------------------------------------------------------------------------+
|                                      DETECTOR ENGINES                                             |
|  +--------------------+  +--------------------+  +--------------------+  +---------------------+  |
|  |   Cost Anomaly     |  |     Duplicate      |  |  Delay Detection   |  | Financial/Physical  |  |
|  | (Robust Z, Peer)   |  | (Embeddings, Sim)  |  | (Slippage, Overdue)|  | (Gap, Milestone)   |  |
|  +---------+----------+  +---------+----------+  +---------+----------+  +----------+----------+  |
|            |                       |                       |                        |             |
|            +-----------------------+-----------+-----------+------------------------+             |
|                                                |                                                  |
|                                     +----------v----------+                                       |
|                                     |    Agency Pattern   |                                       |
|                                     | (Bayesian Portfolio)|                                       |
|                                     +----------+----------+                                       |
+------------------------------------------------+--------------------------------------------------+
                                                 |
                                                 v
                               +-----------------------------------+
                               |       CENTRAL RISK ENGINE         |
                               | (Weighted Score, Missing Strategy)|
                               +-----------------+-----------------+
                                                 |
                                                 v
                               +-----------------------------------+
                               |      EXPLAINABILITY SERVICE       |
                               | - Detector Results Collection     |
                               | - Factor Contribution Ranking     |
                               | - Numerical Evidence Extraction   |
                               | - Rule-Based Administrative Text  |
                               | - Actionable Recommendations      |
                               | - Pre-computed UI Visual Tokens   |
                               +-----------------+-----------------+
                                                 |
                                                 v
                               +-----------------------------------+
                               |       STRUCTURED EXPLANATION      |
                               | (Machine-Readable + UI Dashboard) |
                               +-----------------+-----------------+

                                                 v
                               +-----------------------------------+
                               |          FRONTEND & API           |
                               |   GET /projects/{id}/explain      |
                               +-----------------+-----------------+
```

### Deterministic, Evidence-Grounded Ground Truth
> [!IMPORTANT]
> **Strict Non-Hallucination Policy**: Explanations are **NOT** generated by prompting an LLM to guess reasons or fabricate hypothetical stories. Every narrative sentence, metric, badge, and recommendation is calculated deterministically from:
> 1. Verified mathematical detector outputs (Robust Z-scores, pairwise cosine similarities, days overdue, percentage gaps).
> 2. Historical database benchmarks (peer category medians, interquartile ranges, agency completion frequencies).
> 3. Objective project records stored in PostgreSQL.

### Decision-Support Tone
The system adheres to an administrative, decision-support standard:
- **No Accusations**: Words like "fraud", "scam", "corruption", "embezzlement", or "collusion" are prohibited.
- **Objective Framing**: Flagged items are described as "cost variations requiring BOQ review", "schedule slippages", "progress milestones out of sync with disbursements", or "proposals sharing semantic overlap with nearby works".

## 2. Core Schemas & Data Contracts

All models reside in `backend/app/schemas/explainability.py` and are exported through `backend/app/schemas/__init__.py`.

### 2.1 `EvidenceItem`
Captures granular empirical metrics for side-by-side comparison:
```json
{
  "metric_key": "overdue_days",
  "label": "Days Overdue",
  "actual_value": 412,
  "formatted_value": "412 days",
  "reference_value": 0,
  "formatted_reference": "Baseline: On Schedule (0 days)",
  "unit": "days",
  "context": "Project is 412 days past planned completion."
}
```

### 2.2 `ExplanationFactor`
Detailed breakdown for each of the 5 detector dimensions:
- `factor_name`: Human-friendly title (e.g. "Schedule Delay Overrun", "Cost Peer Deviation").
- `detector_name`: Canonical key (`delay_detection`, `progress_mismatch`, `cost_anomaly`, `duplicate_detection`, `agency_pattern`).
- `severity`: `"LOW"`, `"MEDIUM"`, `"HIGH"`, or `"CRITICAL"`.
- `triggered_status`: `true` if detector score >= 30.0.
- `contribution_to_risk_score`: Weighted points added to composite score (score * weight).
- `threshold_used`: Numerical boundary evaluated (e.g. `"> 90 days delay; > 50% schedule slippage"`).
- `actual_value`: Primary observed summary (e.g. `"412 days past schedule (150.0% slippage)"`).
- `expected_reference_value`: Baseline expectation (e.g. `"Planned duration: 275 days"`).
- `evidence`: List of `EvidenceItem` objects for tabular or chart rendering.
- `raw_evidence_dict`: Raw dictionary for backward compatibility.
- `explanation_text`: Factual, objective narrative paragraph explaining the factor.

### 2.3 `DetectorContribution`
Mathematical breakdown of the risk score composition:
- `detector_name`: Identifier string.
- `display_name`: Formatted title.
- `score`: Raw detector score (0 - 100).
- `weight`: Effective aggregation weight (0.0 - 1.0).
- `contribution_points`: score * weight.
- `percentage_of_total`: Percentage share of the overall project risk score.

### 2.4 `RecommendationAction`
Actionable review items with administrative categorization:
- `action_id`: Unique identifier (e.g. `REC-DELAY-01`, `REC-PROG-02`).
- `priority`: `"HIGH"`, `"MEDIUM"`, `"LOW"`.
- `category`: `"Engineering"`, `"Financial"`, `"Administrative"`, `"Field Verification"`, `"Compliance"`.
- `recommendation`: Step-by-step guidance for auditors or administrative officers.
- `target_detector`: Originating detector key.

### 2.5 `UIDisplayCard` & Frontend Tokens
Pre-computed visual aids for frontend widgets:
- `badge_color`: Tailwind/CSS semantic token (`emerald`, `amber`, `orange`, `rose`).
- `badge_label`: Risk severity string.
- `warning_chips`: High-level pill labels (e.g. `["Overdue Schedule", "Progress Gap"]`).
- `score_progress_pct`: Clamped progress bar percentage (0.0 - 100.0).
- `display_cards`: Pre-formatted card objects for dashboard components.

## 3. Evidence Extraction by Detector

| Detector | Metrics Extracted | Baseline / Peer Reference | Trigger Condition |
| :--- | :--- | :--- | :--- |
| **Cost Anomaly** | Sanctioned cost, Robust Z-score, IQR distance, Cost-per-unit | Peer median cost within category & district | Robust Z >= 2.0 or > 50% above peer median |
| **Duplicate Detection** | Pairwise cosine similarity, matched project ID, title, GPS distance | Duplicate similarity threshold (0.80) | Similarity >= 0.80 & physical proximity |
| **Delay Detection** | Days overdue, planned duration, schedule slippage ratio | Scheduled completion target date | Days overdue > 30 or slippage > 25% |
| **Progress Mismatch** | Financial disbursement %, physical completion %, progress gap Delta | Balanced 1:1 milestone-disbursement curve | Delta >= 20% disbursement lead |
| **Agency Pattern** | Agency portfolio size, agency delay rate, anomaly rate, mismatch rate | Minimum sample size N >= 3, district averages | High delay/mismatch frequency across > 3 projects |

## 4. API Endpoints

### 4.1 `GET /projects/{id}/explain`
Retrieves the comprehensive structured explanation for a given project.

**Query Parameters**:
- `recalculate` (boolean, optional, default `false`): If `true`, re-runs all 5 engines and aggregates risk in real-time before generating explanations.

**Responses**:
- `200 OK`: Returns `StructuredExplanation` schema.
- `400 Bad Request`: If project ID format is invalid.
- `404 Not Found`: If project does not exist.
- `500 Internal Server Error`: If an unexpected database failure occurs.

**Alias**:
- `GET /projects/{id}/risk/explanation`

## 5. Verification & Test Suite

The test suites in `backend/tests/test_explainability_service.py` and `backend/tests/test_standardized_detector_results.py` cover:
1. **Schema Validation**: Mandatory fields, ranges, enum serialization for `StructuredExplanation` and `DetectorResult`.
2. **Standardized Detector Contract**: Verified `EngineResult` dual-compatibility and `.to_standardized_dict()` / `.to_detector_result()`.
3. **Individual Concrete Evidence**:
   - Cost Anomaly: Project cost, peer median, deviation multiplier, percentile, robust Z-score, peer IQR, cost overrun.
   - Delay Detection: Planned completion date, actual/evaluation date, delay days, schedule slippage ratio.
   - Progress Mismatch: Financial disbursement %, physical completion %, progress gap $\Delta$, tolerance.
   - Duplicate Detection: Similarity score, matched project ID, matched title, similarity threshold.
   - Agency Pattern: Portfolio size, historical delay rate, mismatch rate, anomaly rate, peer comparison.
   - Explained / Justification: Justification status, missing/insufficient flag, supporting fields inspected.
4. **Synthesis & Sorting**: Contribution ranking (highest risk contribution first), triggered status count.
5. **Action Recommendations**: Correct categorization and priority assignment.
6. **UI Display Helpers**: Badge color mapping, warning chips, and progress bars.
7. **Live Database Testing**: Real MPLADS records evaluated against live PostgreSQL database.
8. **FastAPI Integration**: Full endpoint validation for 200, 404, 400, and recalculation flows across all routes.

## 6. Standardized Common Detector Result Structure

Every detector engine now produces a standardized structured output conforming to the unified `DetectorResult` contract:

```json

  "detector_name": "delay_detection",
  "triggered": true,
  "severity": "high",
  "score": 75,
  "weight": 0.20,
  "contribution": 15.0,
  "threshold": "> 30 days overdue beyond planned completion date",
  "actual_value": "142 days overdue (+58.4% slippage)",
  "expected_value": "Planned completion: 2024-06-30 (Planned duration: 243 days)",
  "reference_value": "As of 2024-11-19",
  "evidence": [
    {
      "metric": "planned_completion_date",
      "label": "Planned Completion Date",
      "value": "2024-06-30",
      "formatted": "2024-06-30"
    },
    {
      "metric": "actual_current_date",
      "label": "Evaluation Reference Date",
```
